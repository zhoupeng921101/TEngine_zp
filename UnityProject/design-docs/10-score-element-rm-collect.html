得分驱动元素生成 + 移除收集 Demo

两件互不相干、同批交付的改动：① 把 合成订单切片的元素生成从「固定概率注入」改成「消除得分驱动数量」——消得越狠、待选区携带的元素越多；② 把 2026-06-11 的独立收集 Demo 切片整套玩法彻底移除，同时甄别保留它与合成订单切片共用的基础设施。

立项信息

一、这一批改什么

需求动机（用户原话）本质
① 得分驱动元素生成「元素生成和消除得分关联，得分高低和元素生成多少关联，这样更灵活」——比固定比例灵活是设计意图。替换合成订单切片里「每填充格 InjectChance=0.30 概率注入」的固定比例模型，改为「该次消除得分 → 元素数量」的得分函数模型。
② 移除收集 Demo收集切片（凑齐 ◆×6/★×5 过关）已完成历史使命，下线。删除收集专属代码 / 预制 / UI 入口 / 测试；甄别保留与合成订单共用的元素基础设施。
为何两件事同批：① 改的是「元素从哪来、来多少」，② 删的是「另一个曾经消费元素的模式」。两者都围绕「元素由候选块携带」这一条共享基础设施——② 删除时必须认准这条设施不能跟着收集玩法一起删，正是 ① 继续依赖它。

二、需求①：消除得分驱动元素生成

2.1 被替换的现状：固定概率注入

合成订单切片现状（见 09·§七）：补牌时对每个候选块的每个填充格按 InjectChance=0.30 概率，从「订单所需类型并集」里抽一个元素注入；辅以消除门控（上一手没消除过则整手干净）与保底计数器（连续 8 次没注入则强制注入一个）。

问题：注入数量与玩家表现脱钩——清一行和清四行，下一批候选块期望携带的元素数一样（都是 0.30×格数），「会消除」没有被奖励到产出上。

2.2 新模型：得分 → 元素预算队列

落子消除触发行/列消除
→
该次消除得分clearScore
= 格数×10 + 行列数²×30
→
得分→数量k = f(clearScore)
得分越高 k 越大
→
入元素预算队列挑 k 个订单所需类型
压入 PendingElements
→
补牌时投放新候选块按填充格顺序
FIFO 抽干队列
  • 触发即得分：每次落子若触发消除，就用该次消除的得分 clearScore 算元素数 k。无消除 → 不入队 → 后续候选块纯方块。开局首手必纯方块（队列初始空）。
  • 预算队列承接：算出的 k 个元素不立即凭空出现，而是压入 MergeState.PendingElements 队列；补牌（BuildPiece）时从队头 FIFO 抽取，按与落子转移一致的「行优先填充格顺序」写入新候选块的 Elements。这沿用 09 既有的「补牌时注入」节奏（元素始终出现在新发的候选块上），改动面最小、可纯逻辑单测。
  • 队列天然满足两个边界：无消除 → 队列不增长 → 候选块干净；得分高 → k 大 → 队列积压多 → 后续候选块携带更多元素。
投放时机取舍（dev 按此实现，列入 §六 待拍板 供用户确认）：采用补牌时抽干队列（推荐）——与 09 现状一致，玩家感知为「狠消一手 → 下一批候选块明显更多元素」。备选「消除当下立即注入到待选区现有未落子块」反馈更即时，但要改两处注入点、且现有未落子块容量有限（0–2 块），复杂度高，列为后续 UX 增强，本批不做。

2.3 得分 → 元素数量映射（核心审定点）

这是用户要审的设计取舍。采用线性系数 + 保底 + 封顶，一个旋钮 ScorePerElement 调松紧：

映射公式： 
k = clearScore <= 0
      ? 0
      : Clamp( CeilDiv(clearScore, ScorePerElement), MinPerClear, MaxPerClear )
常量默认含义 / 理由
ScorePerElement200每 200 分折 1 个元素。略低于一次双消的分值，使单消稳得 1、双消得 2 —— 平滑的「多消多得」直觉。这是「灵活」旋钮：调小更慷慨，调大更吝啬。
MinPerClear1保底：任何成功消除至少产 1 元素，让「产出→合成→订单」循环不会卡在小消除上——契合「会消除就有奖励」的意图。
MaxPerClear4单次消除封顶。四消已是常规上限；4 个 Lv1 足以喂订单又不淹没待选区（一组 3 块约 15 格，即便三次满额消除 = 12 ≤ 15）。挡住超高连消刷爆经济。
MaxPendingElements12队列总积压上限（≈一组候选块容量）。超出则不再入队——避免极端情形下元素积压速度远超候选格承接，扭曲经济。

得分公式clearScore = 被清格数 × 10 + 被清行列数² × 30（复用 Classic 现有计分，lines² 项已天然让多行消除拿更高分→更多元素）。代入典型消除：

消除类型被清格数clearScore→ 元素数 k
无消除000（待选区纯方块）
单行/列880 + 30 = 110⌈110/200⌉=1 → 1
双消（两行 / 行列交叉）15–16≈270–280⌈280/200⌉=2 → 2
三消≈22–24≈500⌈500/200⌉=3 → 3
四消≈29–32≈780⌈780/200⌉=4 → 4
五消及以上（极罕见）36+1100+⌈5.5⌉=6 → 封顶 4
边界处理小结：0 分 → 0 元素（满足「开局/无消除纯方块」）；超高连消 → 封顶 4（不刷爆）；单消 → 保底 1（小消除不空手）。整段是单调递增、确定性（无随机），逐档可单测。

2.4 元素类型选择：需求拉动 + 轮转均摊

队列里这 k 个元素是什么类型，沿用 09 的需求拉动：只从 MergeState.NeededTypes()（当前激活订单所需类型并集）里取，保证产出对订单有用。多个所需类型时按轮转游标均摊（_needRotor 取模递增），让双订单都被喂到。

保底计数器（PitySinceNeeded/PityThreshold）随旧模型一并退役：旧保底是为了兜「概率长期不中饿死订单」；新模型是确定性生成 + 轮转均摊，任何消除都必产 ≥1 且类型轮流覆盖所需，结构上不会饿死某类型，保底失去存在理由。

2.5 被取代 / 退役的旧机制

旧机制（09 现状）去留原因
InjectChance = 0.30（每格概率）删被「得分→数量」确定性映射取代——正是用户要替换的「固定比例」。
RequireClearForInject + ClearedSinceRefill 消除门控删「无消除→无元素」由「无消除→不入队」自动满足，门控冗余。
PityThreshold + PitySinceNeeded 保底删见 §2.4，确定性 + 轮转下不会饿死，保底冗余。
InjectElementsForMergeOrder() 概率注入改写改为「补牌时从 PendingElements 抽干填入」的 DrainPendingElementsInto()。
合成区摄入 IngestElement / 自动配对 / 订单 / 体力 / 悔棋不动① 只改「元素从哪来、来多少」，合成订单切片其余系统零改动。
合成订单的显示分数（订单交付 TotalScore）不动clearScore 仅作元素生成的内部驱动量，不计入玩家的订单得分，合成订单经济展示保持原样。

3.3 命名误导的处理：保留原名 + 文档标注（推荐）

上述保留项中，CollectDemo / CollectWinWindow / CollectClearedElements 三个名字带 Collect，源于它们诞生于收集切片，现已转用——属命名误导（misnomer），而非功能残留。

取舍：本批不改名，文档标注为「已转用的共享设施」。理由：
  • 改名零功能收益，纯属整洁；而 CollectWinWindow 改名需同步改预制 location 字符串 + .prefab 资产 + .meta + [Window] 特性 + 调用点——UI 按 location 字符串加载，一处不同步即运行期找不到窗口，对已交付的合成订单切片是实打实的风险。
  • 与「移除收集时别牵连合成订单」的约束直接冲突：改名恰恰要动合成订单的工作文件。
  • 「移除干净」指的是收集玩法（代码/场景/入口/测试）已下线——这已达成；共享设施带历史名字不等于没删干净。
若用户坚持正名，列为独立低优先级清理任务（建议名：CollectDemo→BlockElementVisual、CollectWinWindow→DemoWinWindow、CollectClearedElements→GatherClearedElements），单独排期、单独回归，不混进本批。见 §六。

四、挂接点 / dev 改动清单（可落地）

先看 ① 落地后「一次落子」的完整元素流时序——入队发生在消除分支内、补牌之前，投放发生在补牌时，两个时机隔了一次交互（这正是「狠消一手 → 下一批候选块更多元素」的玩家感知来源）。各文件的具体改动落点见下表。

五、验收点（给 test 逐条核对）

需求① · 得分→元素映射

  • 映射逐档：ElementsForScore：0→0、110→1、280→2、500→3、780→4、2000→4（封顶）。负/0 分 → 0。
  • 无消除纯方块：连续落子不触发消除 → PendingElements 恒空 → 补牌后候选块 Elements==null。开局首手三块全干净。
  • 消除即入队、补牌即投放：构造一次得分 S 的消除 → 队列恰新增 ElementsForScore(S) 个 → 触发补牌后，新候选块按填充格顺序 FIFO 携带这些元素，类型 ⊆ NeededTypes()。
  • 得分越高越多：四消产出的元素数 > 单消（同 NeededTypes 下）。
  • 类型轮转均摊：双订单不同类型时，连续入队的元素类型轮流覆盖两类，不长期偏科。
  • 积压封顶：连续高分消除使待入队总数超 MaxPendingElements → 队列长度被截断、不超上限。
  • 悔棋回滚队列：落子→引发消除→入队 k 个，悔棋后 PendingElements 恢复到落子前（k 个被撤回），剩余悔棋次数 -1。
  • off 模式零触：MergeOrderMode=false 时落子不入队、不分配 Elements，ElementArr 保持 null。

需求② · 移除干净 + 保留完整

  • 编译通过：删除收集后全工程 0 error（无悬空引用）。
  • 保留集存活：CollectElement / CollectDemo.Glyph/ColorOf / CollectWinWindow / CollectClearedElements 仍在且被合成订单正常引用。
  • 合成订单切片不回归：合成区自动配对 / 订单交付刷新 / 体力扣返补 / 通关（复用 CollectWinWindow）/ 双失败 / 悔棋——既有用例全绿（① 改注入后须重新通过）。
  • 无残留入口：主菜单无「收集 DEMO」按钮；无任何 CollectDemoWindow 引用、无孤儿 .meta。
  • Classic 不回归：Classic 计分（含抽取的 BlockScoring 后）逐数字不变。
运行验证：dev/test 子会话无 Unity MCP，编译 + EditMode 全量单测由 boss 经命令行 batchmode 补跑（沿用 merge-order 路径）。Play 手验（拖拽落子时元素随得分出现在新候选块的目视确认）列人工遗留。

悔棋漏回滚新增的 PendingElements 队列快照深拷贝队列 + 专项用例（§五·悔棋回滚队列）。
抽取 BlockScoring 改动 Classic 计分纯等价抽取，硬约束「Classic 计分逐数字不变」+ 回归；高风险则退内联同公式。
误删共享设施（CollectElement/CollectWinWindow 等）连累合成订单§3.2 保留集清单逐项标注依赖方；编译 0 error + 合成订单回归为硬验收。
映射数值不合手感（太多/太少元素）ScorePerElement 等全为可调常量，test 配平后一处改数即可。
