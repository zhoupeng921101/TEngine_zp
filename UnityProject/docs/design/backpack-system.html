背包系统设计

道具入包 · 使用道具 · 有效期过期结算 · 前后端数据同步

状态:设计定稿(待实现)  ·  归属:服务端权威  ·  端:全栈(Fantasy 服务端 + Unity 客户端)

1 · 目标与归属

为玩家提供一个持久背包:能获得道具并存入、查看、使用道具产生效果、道具到有效期后自动失效。背包内容代表「玩家拥有什么」,属于玩家资产。

归属定性:服务端是道具数据的唯一事实源。 客户端只持有服务端数据的投影,不持权威副本。道具的获得、消耗、过期一律由服务端裁定;客户端的显示与操作都以服务端下发的状态为准。
为什么不放本地: 道具是玩家资产,一旦客户端可写权威值,改存档即可无中生有。留在本地的只有「排序方式、红点已读」这类换设备不必带走的设备偏好。

2 · 数据模型:两轨制

道具按「是否携带独立状态(尤其有效期)」分两轨存储。混成一种结构会在有效期上出错。

轨单位适用道具说明
堆叠轨道具 → 数量材料、碎片、永久道具等无独立状态、可无限合并的道具沿用现有的堆叠持有结构,同种道具只记一个总数
批次轨批次(一次获得一条)限时道具,以及带独立状态(耐久/强化)的道具每条批次记:道具、数量、获得时刻、过期时刻、来源

批次是有效期的最小单位

同一种限时道具,不同时间获得的两批,过期时刻不同,不能合并成一个数量。因此批次轨以「一次获得 = 一条批次」为单位,每条批次独立持有自己的过期时刻。消耗时按过期时刻从早到晚扣减(先出快过期的)。

为什么不把过期塞进堆叠轨: 「道具→数量」结构无法承载每一批各自的过期时刻;强行给整种道具挂一个过期时间,会绑死「同种道具必须同时过期」,与「分批领取、分批过期」的真实语义冲突。

道具定义与道具实例分离

道具的静态定义(名称、图标、品质、堆叠上限、是否有有效期、有效期时长、使用效果、过期是否补偿)走配置表,双端共享,不进玩家数据。玩家数据里只存「拥有哪些、多少、哪批何时过期」。

3 · 有效期

存绝对时刻,不存剩余时长

道具入包时,服务端以权威时钟算出过期的绝对时刻并固化;之后判定只做「当前时刻是否已过该时刻」的比较。

为什么不存剩余时长: 剩余时长需要持续递减、依赖客户端时钟、跨登录难维护。绝对时刻由服务端时钟一次签发、之后只读,稳定可靠。

过期判定用服务端权威时钟

是否过期由服务端裁定。客户端只做展示层倒计时:登录时锚定一次服务端时间基准,倒计时用「过期时刻 − 校正后的当前时间」推算,不信客户端本地系统时间。

为什么不信本地时钟: 玩家改系统时间不得延长或伪造有效期。客户端本地倒计时仅用于显示,过期与否的结论以服务端为准。

惰性过期,不做全库定时扫描

过期清理在玩家真正触碰数据的时刻结算,不跑定时任务全库扫描:

  • 登录拉快照时 — 服务端过滤已过期批次,快照只下发有效道具;对刚过期的批次做一次结算。
  • 使用道具时 — 服务端二次校验目标批次是否已过期,过期则拒绝并回收。
  • 在线时 — 客户端本地倒计时到 0 自行置灰;不需要服务端为每个道具的过期时刻单独推送。
为什么不用定时扫描: 全库扫描删过期道具浪费且时机难控;惰性过期把成本摊到玩家真正读取/使用数据的那一刻,是联网背包的标准做法。

过期补偿

批次过期结算时,若该道具配置了过期补偿,服务端发放补偿(返还资源 / 发邮件)并记流水。补偿是否发放、发放什么,由道具定义决定,挂在惰性过期的结算点上。

4 · 使用道具

专用事务,不并入通用数值变更

使用道具作为一次独立的服务端事务处理:客户端提交「用哪个道具、用几个、请求序号」,服务端校验后执行效果,把「扣道具 + 产出效果」作为一个原子事务落账,再把结果(消耗清单 + 产出清单)回给客户端。

为什么不复用通用数值变更通道: 通用数值变更的前提是「客户端知道自己要加减多少」。而使用道具的产出由服务端逻辑裁定(开箱随机产出、buff、回血),客户端预测不了;且「扣道具 + 产出」必须原子、可回滚,单条数值增减表达不了。这不是绕过权威造新通道,而是权威体系内的一个业务动作。

幂等:请求序号防重复扣

使用请求携带唯一请求序号。服务端对同一玩家的同一序号去重:重复到达的请求返回首次结果,不重复执行。

为什么必须幂等: 弱网重连会导致同一使用请求被发送两次。没有请求级去重,就会双扣道具、双发产出。频率闸(限流)挡不住「同一请求被重发」,必须按请求序号去重。

客户端乐观边界

客户端可做轻量乐观反馈(按钮置灰、数量减一动画),但产出必须等服务端结果,不预测产出;服务端拒绝则回滚乐观显示。

5 · 数据同步

路径触发机制
读 · 初始化登录背包并入登录快照一次性下发(堆叠轨全量 + 批次轨已过滤过期),不另起查询请求
写 · 获得掉落 / 购买 / 任务奖励等服务端行为服务端入包 + 记流水,再增量推送给在线客户端;客户端不能自行造道具
写 · 使用客户端发起使用事务(见 §4),结果回执 + 增量推送同步背包变更
推送 · 保鲜背包发生变更背包增量推送:携带变更后的道具/批次状态,推给该玩家在线会话

推送语义与对账

  • 推送携带「变更后的状态」,不是需要客户端累加的相对流水。
  • 推送丢失 = 下次登录拉快照对齐,不做重试;离线则丢弃。
  • 客户端乐观值与服务端下发值不一致时,以服务端为准强制校正。
为什么复用快照 + 增量推送: 现有玩家数据同步已是「登录快照初始化 + 增量推送保鲜 + 登录兜底对齐」骨架。背包沿用同一骨架,不自造查询/同步通道。

6 · 边界与规则

  • 堆叠上限 / 背包容量 — 由服务端按道具定义校验。超上限 / 背包满的处理(拒绝入包 / 溢出转邮件)按业务定,但裁决在服务端。
  • 流水 — 获得、使用、过期、补偿都记账,可追溯,用于丢件纠纷核对。
  • 旧档兼容 — 老玩家没有批次轨数据,登录时自动补为空,不报错、不丢原有堆叠道具。

7 · 验收标准

行为级、可观测。实现交付以此逐条核对。

A · 获得与存入 服务端

  • AC-1 通过服务端行为获得堆叠道具后,该道具数量在服务端正确累加,并推送到在线客户端;客户端背包显示更新。
  • AC-2 获得限时道具后,服务端生成一条批次,其过期时刻 = 获得时刻 + 配置时长(以服务端时钟为准)。
  • AC-3 同种限时道具分两次获得,服务端产生两条独立批次,各自过期时刻不同,不被合并。
  • AC-4 每次获得都写入流水,含来源标识。
  • AC-5 客户端无法通过任何本地操作凭空增加道具;道具增加只能源于服务端下发。

B · 使用道具 服务端 客户端

  • AC-6 使用道具后,服务端原子完成「扣道具 + 产出效果」,回执含消耗清单与产出清单;客户端据回执刷新。
  • AC-7 数量不足 / 道具不存在 / 已过期 / 未达使用条件时,服务端拒绝,不扣不产出,回执带明确原因。
  • AC-8 同一使用请求被重复提交(相同请求序号),服务端只执行一次,重复请求返回首次结果,道具不被双扣。
  • AC-9 使用限时道具时按过期时刻从早到晚扣减(先消耗快过期的批次)。
  • AC-10 客户端乐观反馈后若服务端拒绝,客户端回滚到服务端值。

C · 有效期与过期 服务端 客户端

  • AC-11 登录拉快照时,已过期批次不出现在下发的背包里。
  • AC-12 试图使用已过期道具被服务端拒绝并回收该批次。
  • AC-13 配置了过期补偿的道具过期后,玩家收到补偿(资源返还 / 邮件),且补偿记入流水。
  • AC-14 客户端背包倒计时基于服务端时间基准;修改客户端本地系统时间不改变服务端的过期判定。
  • AC-15 在线时客户端倒计时到 0,该道具本地置灰;此后对它的使用请求被服务端拒绝。

D · 同步一致性 服务端 客户端

  • AC-16 背包全量随登录快照一次性到达客户端,无需额外查询请求。
  • AC-17 背包任何变更(获得/使用/过期)都推送到该玩家全部在线会话。
  • AC-18 推送丢失后重新登录,客户端背包与服务端一致(快照兜底对齐)。
  • AC-19 客户端乐观值与推送值冲突时,最终显示为服务端值。

E · 边界与兼容 服务端

  • AC-20 获得超过堆叠上限 / 背包容量时按既定策略处理(拒绝或溢出转邮件),不产生非法状态。
  • AC-21 无背包批次数据的老玩家登录不报错,原有堆叠道具不丢失。

8 · 关键决策记录

决策取舍
两轨制(堆叠 + 批次)相对「单一数量字典」:批次轨才能表达分批过期;相对「全部实例化」:堆叠轨保留避免无状态道具膨胀成大量实例
有效期存绝对时刻相对「存剩余时长」:免持续递减、免依赖客户端时钟、跨登录稳定
惰性过期相对「定时全库扫描」:省成本、时机随玩家访问自然触发
使用道具用专用事务相对「复用通用数值变更」:承载服务端裁定的产出 + 原子回滚,通用增减做不到
请求序号幂等相对「仅靠限流」:限流挡不住同一请求重发导致的双扣
本稿为设计意图与行为级验收,不含代码符号/文件路径/改动清单——实现层定位在实现段依代码现场推导。
有效期语义:限时道具为「分批领取、分批过期」,批次轨按 §2 以批次为最小单位。
