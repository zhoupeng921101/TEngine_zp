# conventions.md — 持久文件写作规约

> 单一信息源。需要这套规则的地方**引用本文件,不复制内容**——副本会各自过时。

**适用**:所有 agent(主会话与流水线角色)写任何会被后续读取的持久文件(文档、状态文件、笔记、配置说明、代码内的散文型注释如类头/doc-comment…)。
**不含**:工具生成物(Luban .cs 行类/表类、bin 等,改源重导而非手编,「勿手改」见 tengine-dev references)、二进制(prefab/.meta,无散文)。
代码注释只受规则5(语体)+ 规则1(不写过程/diff 叙事)约束;

**根因**:一份文件混了保质期不同的内容——短命的"过程"渗进长命的"正文"又没人清,就腐烂(过时、自指、矛盾)。

## 内容分层(按保质期)

| 层 | 保质期 | 内容 | 怎么维护 |
|----|--------|------|----------|
| **规范** | 永久(直到被替换) | 指令、不变量、当前事实 | 覆盖式:新的替换旧的,不追加 |
| **理由** | 随所注的规范 | 为什么这么设计、有什么坑 | `>` 旁注,须能独立成立。**与所注规范同生同死:改规范必检旁注,孤儿旁注即删** |
| **工作状态** | 任务期 | 交接区、进行中状态、待办 | 须可识别所属任务;**任务关闭时清空或归档**(流水线由 boss 关单事务执行) |
| **过程** | 一次性 | 改了啥、来回讨论、临时备注 | 默认不入文件(交 git);需就地留痕才进日志段 |

## 核心规则

1. **隔离** — 过程性内容与正文分开。**首选:根本别写进文件**,交给版本历史。仅当必须就地追溯,才另设独立「日志」段(或单独文件)容纳——散文型文档(设计/README/教程)通常不需要,保持流畅正文即可。正文永不掺入过程。
2. **准入·脱离对话成立** — 进正文(含理由旁注)的句子要脱离当下对话仍成立:禁指代词("你说的"/"刚才")、禁 diff 叙事("从 X 改成 Y",历史已记录)。测试:*半年后外人读到是"原来如此"还是"在跟谁说话"?*
   - 反例:`按你说的把超时从 30s 改成 60s`
   - 正例:`超时 60s` + 旁注 `> 30s 在弱网下误杀(2026-06 实测)`
3. **准入·可推导的不记录** — 正文不记录可从他处推导/查询的事实(进度、状态、其他文件内容的转述汇总)。副本必漂移:要么引用来源,要么用时现场推导。
4. **命名·用公共词汇** — 给新概念/流程/角色命名,用行业或职场的公共词和术语,不自造圈外查无此词的词。
5. **语体·简洁说明文** — 正文用简洁陈述句,不用拟人化/口语比喻。
   > 比喻看似省字又显在行,却只对共享该比喻的圈内读者清晰,会顺上下文漏进对用户的呈报(2026-06-13 实例:「进程被打死」「agent 死在返回 verdict 的尾巴上」被用户点名问是不是黑话)。逐词拉黑是补丁——换个场景照样冒新比喻;要拨的是整个语体:默认目标设为「简洁说明文」,不是「聊故障的聊天体」。

## 收尾必做(自检)

由做出改动的 agent 在返工收尾(任务完成、阶段切换、大改后)对自己改过的文件逐句过一遍:

- [ ] 过程性内容不在正文(交 git 或日志段)(规则1)
- [ ] 正文无可推导事实的副本(进度/状态/转述汇总)(规则3)
- [ ] 正文无拟人/口语比喻(规则5)
- [ ] 工作态内容可识别所属任务;已关闭任务的工作状态已清空/归档(分层表·工作状态)
- [ ] 被改动规范的旁注仍成立(无孤儿理由)(分层表·理由)

## 交叉检(验收方必做)

自检是最弱的检查点:改动者自带对话上下文,刚写完最容易盲。凡有验收环节的流程,**验收方**对改动者动过的持久文件执行上方「收尾必做」自检 + 抽查(流水线:test 在 code review 时查 dev,boss 在收产出时查各环节)。无验收环节的散件改动:agent 跨会话无记忆,「隔会话再自查」无人负责触发,故改为可推导留痕——在 commit message 注明已跑本节自检(供后续会话 grep 核);规则栈类散件另有手动 `/audit` 兜底。

## 规则准入(新增常驻指令前必查)

常驻指令(项目根 CLAUDE.md / `.claude/rules` / `.claude/skills` 与 `.claude/agents` 下规则文件 / `pipeline/memory` 各文件头)也是持久文件,准入前过以下提问:

1. **查重** — grep 整个规则栈(上一句列出的全部文件);模型与框架内置无法 grep,默认用人工自答「这条是不是模型默认就会做」并留一句理由。仅当真争议、自答吵不清时才动用**行为探针**(成本高:干净会话喂场景跑 2-3 次防采样噪声、再注入新规则跑对照,基线侧测「是否重复」、注入侧测「是否有效」)。探针是高争议时的备用手段、非每次准入必跑——长期零触发则按审计死规则路径评估降级。
2. **分层** — 这条是性格宣言还是操作程序?同层重复才删,跨层是补充。
   > 例:「敢反对」是性格,「先独立成判再对照用户立场」是程序——不算重复。
3. **触发** — 举得出「没有这条会做错」的具体场景吗?举不出 = 死规则,不进。**并问复发性**:该场景是会反复发生的结构性问题,还是一次性事故(工具/通知损坏、单次环境抖动、一次措辞失误)?一次性事故优先 git 回滚或一次口头提醒,不上升为常驻规则;只有论证出复发机制才进常驻信道。
4. **反噬** — 被过度执行会怎样?无条件指令会被当成默认动作(如「多用列表」导致 bullet 泛滥),改成条件触发再进。
5. **反向冲突** — 新规则是否与既有条款矛盾?是否使某既有条款过时(被涵盖/被替代)?有 → 在同一次改动里改或删旧条款,不留给定期审计(此刻上下文最全,改旧成本最低)。
