# conventions.md — 持久文件写作规约

> 单一信息源。需要这套规则的地方**引用本文件,不复制内容**——副本会各自过时。

**适用**:所有 agent(主会话与流水线角色)写任何会被后续读取的持久文件(文档、状态文件、笔记、配置说明、代码内的散文型注释如类头/doc-comment…)。一次性临时文件除外。**不含**:工具生成物(Luban .cs 行类/表类、bin 等,改源重导而非手编,「勿手改」见 tengine-dev references)、二进制(prefab/.meta,无散文)。代码注释只受规则6(语体平实)+ 规则1(不写过程/diff 叙事)约束;规则2「禁指代词」对代码注释豁免——「这里/此处」在代码上下文是合法本地指代。

**根因**:一份文件混了保质期不同的内容——短命的"过程"渗进长命的"正文"又没人清,就腐烂(过时、自指、矛盾)。

## 内容分层(按保质期)

| 层 | 保质期 | 内容 | 怎么维护 |
|----|--------|------|----------|
| **规范** | 永久(直到被替换) | 指令、不变量、当前事实 | 覆盖式:新的替换旧的,不追加 |
| **理由** | 随所注的规范 | 为什么这么设计、有什么坑 | `>` 旁注,须能独立成立。**与所注规范同生同死:改规范必检旁注,孤儿旁注即删** |
| **工作态** | 任务期 | 交接区、进行中状态、待办 | 须可识别所属任务;**任务关闭时清空或归档**(流水线由 boss 关单事务执行) |
| **过程** | 一次性 | 改了啥、来回讨论、临时备注 | 默认不入文件(交 git);需就地留痕才进日志段 |

> **归层有歧义时的裁决**:按「覆盖式更新是否真丢历史(git 兜不住)」判——是(state、audit-log、memory 这类被覆盖即丢在途历史的文件)→ 须就地(工作态/日志段);否(散文档、可 git 追溯)→ 交 git 不入文件。这是规则1 例外与规则4 旁注已隐含的判据,提炼为可直接援引的一句。

> **注入信道也是一层**:本项目把根 `CLAUDE.md` 与 `.claude/rules/` 下所有 .md(**递归**,含子目录)自动注入每个上下文窗口(常驻开销,harness 行为、无 settings 控制)。该信道只放「每轮都相关」的规范层(规则/不变量);日志/历史/数据(过程层、低频追溯)放到注入路径**外**(如 `.claude/rules-archive/`,与 `rules/` 同级、不在递归注入范围内)、按需 Read。判据:这份内容**每轮都用得上**吗?是 → 可常驻;否(偶尔查)→ 移出注入路径。放错信道 = 每窗口白付一次,越长越贵(2026-06 实测:audit-log 积到 27KB 仍每窗口全量注入;关键——注入是**递归**的,把历史挪进子目录 `.claude/rules/archive/` 不解决问题,子目录照样注入,须把归档移出 `rules/` 本身才真正降到数 KB)。

## 六条规则

1. **隔离** — 过程性内容与正文分开。**首选:根本别写进文件**,交给版本历史。仅当必须就地追溯、且读者看不到 git 时,才另设独立「日志」段(或单独文件)容纳——散文型文档(设计/README/教程)通常不需要,保持流畅正文即可。正文永不掺入过程。
2. **准入·脱离对话成立** — 进正文(含理由旁注)的句子要脱离当下对话仍成立:禁指代词("你说的"/"刚才")、禁 diff 叙事("从 X 改成 Y",历史已记录)。测试:*半年后外人读到是"原来如此"还是"在跟谁说话"?*
   - 反例:`按你说的把超时从 30s 改成 60s`
   - 正例:`超时 60s` + 旁注 `> 30s 在弱网下误杀(2026-06 实测)`
3. **准入·可推导的不记录** — 正文不记录可从他处推导/查询的事实(进度、状态、其他文件内容的转述汇总)。副本必漂移:要么引用来源,要么用时现场推导。

   > 实证:流水线 boss 曾把「当前阶段」复制进自己的 state,测试早已 PASS 而记录停在「进行中」。规则副本同理——见篇首「单一信息源」。

4. **清理** — 日志段不无限长:任务关闭,或**该日志段**超约定上限(默认 ~200 行,按段计、非按文件计)即归档或删。归档位置:与该文件同目录的 `archive/`。**例外:文件本身落在自动注入路径(`.claude/rules/` 下,递归含子目录)时,同目录 `archive/` 子目录仍被注入,归档须移出 `rules/`(如 `.claude/rules-archive/`,与 `rules/` 同级)——见「内容分层·注入信道」。**

> 为何只有"看不到 git"的文件需要日志段:这类文件的覆盖式更新会真丢历史(git 兜不住),日志段是它唯一的就地追溯。

5. **命名·用公共词汇** — 给新概念/流程/角色命名,用行业或职场的公共词,不自造圈外查无此词的词。自检判据是**对本项目读者(各 agent + 用户)是否共享、是否望文生义**:望文生义的公共词组合(如「规则栈」「注入信道」)即便项目外搜不到原词也合法;圈外查无、且读者读不懂或含比喻的(如「运行门」)才是病。「项目文件之外搜得到同义用法吗」只是辅助信号,不是判据本身。确需私有概念时,用公共词组合出望文生义的名字。历史归档里的旧名冻结不回改。

   > 私有词汇会顺着上下文污染所有读者(含各 agent)的语言,最终漏进对用户的呈报,而用户没读过定义它们的文件(2026-06-13 实例:自造词「棒」「运行门」等在对话中累积到用户读不懂,经用户拍板全栈换为「环节」「运行验证」等公共词)。判据是「对读者是否共享」:行业公共术语合法且应当用,私造词才是病。

6. **语体·平实说明文** — 正文用平实陈述句,不用拟人化/口语比喻(死、打死、收口、撞、串、尾巴、挂了 一类)。判据同上条:*外人一遍读懂、不被比喻带偏吗?* 平实改写:进程「被打死」→ 终止/异常退出;「死在落盘之前」→ 写入前异常退出;任务「收口」→ 结束/收尾;问题「撞到一起」→ 重合。行业术语(编译/域重载/落盘/prefab)合法照用——病的是比喻,不是术语。

   > 比喻看似省字又显在行,却只对共享该比喻的圈内读者清晰,会顺上下文漏进对用户的呈报(2026-06-13 实例:「进程被打死」「agent 死在返回 verdict 的尾巴上」被用户点名问是不是黑话)。逐词拉黑是补丁——换个场景照样冒新比喻;要拨的是整个语体:默认目标设为「平实说明文」,不是「聊故障的聊天体」。

## 收尾必做(自检)

由做出改动的 agent 在返工收尾(任务完成、阶段切换、大改后)对自己改过的文件逐句过一遍:

- [ ] 正文无指代词、无 diff 叙事(规则2;可先跑 lint,再人工补查:`grep -nE '刚才|上面(说|提)的|你(说|提)的|现在改成|从.*改成|本次(修改|调整)' <file>`)
- [ ] 正文无拟人/口语比喻(规则6;常见offender可 lint:`grep -nE '打死|挂了|收口|死在|尾巴上' <file>`;此名单是正文禁用集的保守子集——撞/串等会误命中碰撞/字符串等合法术语故不入正则,0 命中≠语体过关;比喻开放,grep 非穷尽,仍须人工通读判语体)
- [ ] 正文无可推导事实的副本(进度/状态/转述汇总)(规则3)
- [ ] 过程性内容不在正文(交 git 或日志段)(规则1)
- [ ] 工作态内容可识别所属任务;已关闭任务的工作态已清空/归档(分层表·工作态)
- [ ] 被改动规范的旁注仍成立(无孤儿理由)(分层表·理由)
- [ ] 日志段未超长(超了就归档/删)(规则4)
- [ ] 规则只此一份,别处是引用(篇首·单一信息源)

## 交叉检(验收方必做)

自检是最弱的检查点:改动者自带对话上下文,刚写完最容易盲。凡有验收环节的流程,**验收方**对改动者动过的持久文件执行上方 lint + 抽查(流水线:test 在 code review 时查 dev,boss 在收产出时查各环节)。无验收环节的散件改动:agent 跨会话无记忆,「隔会话再自查」无人负责触发,故改为可推导留痕——在 commit message 注明已跑本节 lint(供后续会话 grep 核);规则栈类散件另有关单 `/audit` 兜底。

## 规则准入(新增常驻指令前必查)

常驻指令(项目根 CLAUDE.md / 本文件 / `.claude/skills` 与 `.claude/agents` 下规则文件 / `pipeline/memory` 各文件头)也是持久文件,准入前过六问:

1. **查重** — grep 整个规则栈(上一句列出的全部文件);模型与框架内置无法 grep,默认用人工自答「这条是不是模型默认就会做」并留一句理由。仅当真争议、自答吵不清时才动用**行为探针**(成本高:干净会话喂场景跑 2-3 次防采样噪声、再注入新规则跑对照,基线侧测「是否重复」、注入侧测「是否有效」)。探针是高争议时的备用手段、非每次准入必跑——长期零触发则按审计死规则路径评估降级。
2. **分层** — 这条是性格宣言还是操作程序?同层重复才删,跨层是补充。

   > 例:「敢反对」是性格,「先独立成判再对照用户立场」是程序——不算重复。

3. **触发** — 举得出「没有这条会做错」的具体场景吗?举不出 = 死规则,不进。**并问复发性**:该场景是会反复发生的结构性问题,还是一次性事故(工具/通知损坏、单次环境抖动、一次措辞失误)?一次性事故优先 git 回滚或一次口头提醒,不上升为常驻规则;只有论证出复发机制才进常驻信道。
4. **反噬** — 被过度执行会怎样?无条件指令会被当成默认动作(如「多用列表」导致 bullet 泛滥),改成条件触发再进。
5. **归位** — CLAUDE.md=表达协作/任务路由/编码红线;本文件=持久文件写作;agent 定义=角色职责;pipeline SKILL.md=编排流程。放错层的规则后人找不到,会在别处再被写一份——归位是查重的前提。**并核信道**:文件落在自动注入路径(范围见「内容分层·注入信道」)= 每窗口常驻,只放每轮相关的规范层;日志/历史/数据放注入路径外按需读。
6. **反向冲突** — 新规则是否与既有条款矛盾?是否使某既有条款过时(被涵盖/被替代)?有 → 在同一次改动里改或删旧条款,不留给定期审计(此刻上下文最全,改旧成本最低)。

## 规则审计(防规则栈腐烂)

触发:pipeline 关单事务发现规则栈本次有改动时顺带执行,或用户手动 `/audit`。先查增量:规则栈自上次审计(基线记 `.claude/rules/audit-log.md`)无改动 → 记「无变化,跳过」即止,不做全量;有改动才查三样:

> `.claude/` 下 skill/agent 规则文件纳入射程的原因:平时无人改动、也不在任何验收环节的交叉检范围内,规则副本在那里腐烂最久才被发现(2026-06 实测:编码红线副本散布 4 处,其中 3 处引用了已不存在的目录)。

> **准入与审计分工不重合,不可合并**:准入六问在新规则入栈前一次性把关,本节审计对已入栈条款定期复查——两者查同一批问题(重复/死规则/矛盾),但覆盖不同时间点:新规则可能准入时无矛盾、后续别的改动使其过时(准入管不到),旧规则也可能从未走过准入(早期直接写入)。

1. **重复** — 同一行为多处有源;疑似与模型/框架内置重复的条款,跑行为探针复核(基线已达标 → 删除候选)。
2. **死规则** — 连续多轮审计都举不出触发实例的条款 → 删除候选(单次窗口不判死,看累计)。
3. **矛盾** — 条款互相冲突,或与近期实际行为冲突。
4. **信道匹配**(仅当注入集有增减时)— 本次有文件新进/移出自动注入路径(范围见「内容分层·注入信道」)→ 核它该常驻注入(规范层每轮相关)还是该移出按需读(日志/数据层)。无增减则跳过:注入集变化罕见,非每轮查。
5. **净增趋势**(增量审计顺手记一行,只观察不强删)— 记本轮注入态(`.claude/rules/` 下所有 .md)总行数 vs 上轮;连续多轮净增且无对应删除 → 升为「总量复查」候选。不设硬数字上限(硬上限会逼出为达标误删,见准入#4)。
6. **孤儿旁注**(仅当本次有规范被覆盖/删除时)— 核被改/删规范的 `>` 旁注是否随之清理,并抽查若干现存旁注其父规范是否还在、还成立(孤儿旁注即删)。无规范增删则跳过。

审计结论追加 `.claude/rules/audit-log.md`;**删除候选先报用户拍板,不静默删**——审计方可能没见过该规则触发的会话。
